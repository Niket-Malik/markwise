# Deployment guide

## Current deployment state

No public deployment has been created or verified. This workspace has no Git remote or deployment credentials, and Docker is unavailable. `render.yaml` prepares a Render Blueprint with a FastAPI Docker web service, a Next.js Docker web service, and a daily retention cron job. It expects a Git repository connected to Render and the external secrets listed below. Never treat the planned service names or hostnames as live URLs.

## Prepared architecture

- Render Singapore region: FastAPI backend (`/health`), Next.js frontend, and daily retention worker. Render terminates HTTPS. The API image runs Alembic in the pre-deploy phase; web startup runs Uvicorn only. The cron invokes `python -m app.retention` at 04:15 UTC daily.
- Neon PostgreSQL with `vector` extension: configure the Neon pooled connection string as `DATABASE_URL`. Runtime and Alembic convert Neon’s standard `postgresql://`/`postgres://` URL to `postgresql+psycopg://`. Use SSL (`sslmode=require`) and enable pgvector; migrations also create the extension if permitted. Do not expose a database port publicly.
- Cloudflare R2: private bucket, endpoint `https://<ACCOUNT_ID>.r2.cloudflarestorage.com`, region `auto`, bucket and R2 S3 credentials. R2 provides managed encryption at rest; the app deliberately omits AWS SSE headers because R2 rejects them. Restrict the key to the app bucket and required object operations.
- AI provider: OpenAI-compatible endpoint, chat model, vision-capable model, and 1536-dimension embedding model. The app only sends workspace data when an admin enables external AI. Set `AI_API_KEY` through Render secret management.

## Deploy steps requiring account access

1. Put this existing project in a GitHub/GitLab repository and connect that repository to Render. This workspace currently has no `.git` directory or remote, so there is no source repository Render can deploy. Do not commit `.env` or secrets.
2. In Render, create a Blueprint from the repository’s `render.yaml`. Review the service plans and estimated cost before accepting; the API plan is configured as `1c-2g`, and the frontend/cron use `0.5c-512mb`.
3. Create or select a Neon project, enable pgvector, and provide its pooled connection string as the Blueprint’s `DATABASE_URL` secret. Keep `sslmode=require` in the URL.
4. Create a private R2 bucket and scoped API token. Provide `S3_ENDPOINT_URL`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, and `S3_SECRET_ACCESS_KEY` in Render’s secret prompts.
5. Provide the AI provider’s API key and actual model IDs as `AI_API_KEY`, `AI_MODEL`, and `VISION_MODEL`. `EMBEDDING_MODEL` defaults to `text-embedding-3-small`; it must return 1536 dimensions. If there is no AI key, set provider/model configuration accordingly and treat AI analysis as unavailable.
6. Deploy and inspect the Render build, pre-deploy migration, web health, and cron logs. Render generates the API secret. The frontend reads the API host from the API web service reference and builds its HTTPS base URL.
7. Confirm the deployed frontend origin equals the backend’s `CORS_ORIGINS`. If Render assigns a different hostname, update the API allowlist and redeploy. Confirm TLS redirects and configure shared edge rate limiting/monitoring at the public edge before inviting users.

Render Blueprint provisioning may not be able to resolve a `sync:false` secret from an upstream service into the cron service in every account/setup. If the retention worker fails to receive Neon/R2 secrets, enter the same values in that service’s protected environment settings and verify one successful run in cron logs. Do not paste secrets into chat or source files.

## Environment values

The Render Blueprint defines the public and non-secret settings. Required secret inputs are `DATABASE_URL`, `S3_ENDPOINT_URL`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `AI_API_KEY`, `AI_MODEL`, and `VISION_MODEL`. `SECRET_KEY` is generated by Render. The backend also supports `CORS_ORIGINS`, `ACCESS_TOKEN_MINUTES`, `AI_API_BASE_URL`, `EMBEDDING_MODEL`, `AI_TIMEOUT_SECONDS`, and `OCR_LANGUAGE`. Set the CORS origin to the exact frontend HTTPS origin. Set secrets only in service secret settings.

## Local Compose checks

1. Copy `.env.example` to `.env`, set a unique random `SECRET_KEY` and `POSTGRES_PASSWORD`, and leave `DATABASE_URL` blank for Compose to construct a local URL.
2. Run `docker compose config`, then `docker compose up --build`.
3. Check `http://localhost:8000/health` and `http://localhost:3000`; exercise a workspace workflow. Compose uses PostgreSQL/pgvector, API migration startup, frontend health dependency, and a separate periodic retention worker.

Compose is a development stack. It does not replace production secret management, backups, shared rate limiting, external monitoring, or TLS configuration.

Only mark deployment complete after actually running each check with production services:

- Confirm Render deployment succeeds, Alembic reaches head, `/health` reports database connected, frontend responds over HTTPS, and CORS accepts only the expected origin.
- Register a dedicated test workspace, log in, verify role restrictions and cross-workspace isolation, upload a document to R2, import and admin-confirm a guideline, and verify retention deletion removes both object and metadata.
- With external AI explicitly enabled in that test workspace, verify review analysis uses real model responses and real pgvector retrieval/citations. Exercise unsupported claim `CANNOT VERIFY`; inspect source citation excerpts and verify the vision workflow with a real image/reference logo. Never substitute fabricated citations or canned results.
- Verify dashboard values against the test workspace’s records; check HTTPS, headers, edge rate limits, logs, database backups, R2 policy and purge outcomes. Run the frontend with keyboard and screen-reader checks.

The current local backend suite uses SQLite and mocked AI/S3 adapters. The frontend build and Node smoke/accessibility checks are not browser end-to-end tests. The local SQLite migration check does not prove Neon/pgvector compatibility. Docker, live provider, Neon, R2, production workflow and public URL checks remain unverified until services and authenticated access are supplied.
